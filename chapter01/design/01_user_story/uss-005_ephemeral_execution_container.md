# USS-005 — Run code in an ephemeral execution container

USS-005 runs inside an agent container created by USS-002, from the image created by USS-003. It uses the in-container Docker daemon that those stories provide.

Status: not yet implemented. No `run_ephemeral_container` source exists in `packages/`, and `Dockerfile.agent` does not install it. The in-container daemon it relies on is provided by the image (`tini` as PID 1 starts `dockerd` as root; settings in `/etc/docker/daemon.json`; user `agent` uid/gid 1001 in group `docker`).

## Participants

| Participant | Role |
|---|---|
| Agent | The `claude` process running as the non-root agent user (UID 1001) inside the agent container; asks for code to be run |
| Execution tool | Go executable `run_ephemeral_container`, part of the agent image, run by the agent user inside the agent container; creates, starts, waits for and removes one ephemeral container per run |
| Agent container | gVisor sandbox from USS-002; hosts the in-container Docker daemon |
| In-container Docker daemon | `dockerd` started by the container init as root inside the agent container; creates the ephemeral containers |
| Ephemeral container | Short-lived container for one run; removed when the run ends |
| Agent workspace | `/workspace` inside the agent container (the per-agent folder from USS-002) |

Workspace layout (paths relative to `/workspace`):

| Path | Content |
|---|---|
| `src/` | Source code |
| `.venv`, `.npm-env`, `.conda-env` | Dependency environment folders (hidden dot folders), for pip, npm and conda |
| `.output/` | Log folder; one sub-folder `<runID>` per run |

## Goal

As an agent, I want to run code, or install its dependencies, in a fresh, throwaway container by calling a single Go executable with a subcommand (`run` or `install`), so that the container has only the access its subcommand needs (for `run`: read-only access to the workspace, no network, no access to the agent's credentials or tools), the logs are written only to `/workspace/.output`, and nothing is left behind when it ends.

Isolation claim (precise):

- The ephemeral container separates the executed code from the agent: its credential mounts, home directory, network route and tools are not visible to the code.
- It is NOT a boundary against the agent. The agent user has access to the in-container Docker socket and can therefore run any container with any setting the in-container daemon allows; this is effectively root inside the agent container. This is a declared deviation from SSR-AGC-011 (non-root agent workload with no capabilities). The containing boundary is the gVisor sandbox of the agent container (USS-002); the host-side network controls (USS-004) stay out of the agent's reach.
- The subcommands restrict what the tool does, not what the agent can do: the agent has the Docker socket and can bypass the tool (consistent with the SSR-AGC-011 deviation above).
- The ephemeral container runs under the in-container daemon's default runtime inside gVisor. It is not a second gVisor sandbox.

## Invocation

The tool takes a subcommand. Each subcommand maps to a fixed, predefined image; the image names (`TBD`) are compiled into the binary and are not selectable by argument. There is no `--image` argument.

Subcommands for now: `run` and `install`. More (e.g. `test`, `debug`) may come later.

Run by the agent user inside the agent container.

### `run`

```
run_ephemeral_container run [--timeout <seconds>] -- <command> [args...]
```

Executes code from `src/` using the dependencies preinstalled in the env folders.

| Argument | Required | Meaning |
|---|---|---|
| `--timeout <seconds>` | no | Wall-clock limit of the run; default `TBD` |
| `<command> [args...]` | yes | Command run inside the ephemeral container, with `/workspace` as working directory |

### `install`

```
run_ephemeral_container install <manager> [--timeout <seconds>] [-- <manager args...>]
```

No user code is executed; only the dependency manager runs. The tool sets the entrypoint to the manager binary itself; the agent cannot supply an arbitrary command. Manifests (e.g. `src/requirements.txt`, `src/package.json`) are read from the read-only `src/`.

| Argument | Required | Meaning |
|---|---|---|
| `<manager>` | yes | Dependency manager; one of the table below |
| `--timeout <seconds>` | no | Wall-clock limit of the run; default `TBD` |
| `-- <manager args...>` | no | Arguments passed to the manager binary |

| Manager | Target env folder (read-write) |
|---|---|
| `pip` | `/workspace/.venv` |
| `npm` | `/workspace/.npm-env` |
| `conda` | `/workspace/.conda-env` |

The set of managers is `TBD` and extendable.

Each run gets a `runID` generated by the tool. The ephemeral container is named `ephemeral-<runID>`.

## Build and delivery (Go)

- `run_ephemeral_container` is planned as a static Go binary for `linux/amd64`. Where it is built is `TBD` (not implemented; no Go source or build step exists yet).
- Delivery is planned through USS-003: `Dockerfile.agent` is to install it at `/usr/local/bin/run_ephemeral_container` (`root:root`, mode 755). Today `Dockerfile.agent` has no such step (open item).
- It is not setuid; `no-new-privileges` (SSR-AGC-010) would block that. It reaches the in-container Docker daemon through the Docker socket with the agent user's own access.

## Preconditions

- USS-002 is complete: the agent container is running and armed.
- The in-container Docker daemon is running and its socket is reachable by the agent user (agent user is in the in-container `docker` group).
- The in-container daemon runs with no bridge and no iptables management (`"bridge": "none"`, `"iptables": false`, `"ip6tables": false`), and its data root `/var/lib/docker` lives inside the agent container, on a size-bounded `tmpfs` (2g, USS-002), not on a host path (SSR-AGC-004).
  Note: these settings, the default runtime `runc` and the other daemon settings are fixed in the image's `/etc/docker/daemon.json` (USS-003, Image content), not passed as `dockerd` flags (the image starts plain `dockerd`); a setting given both as a flag and in the file stops `dockerd` from starting.
- `/workspace/.output` exists in the workspace.
- The image is the fixed image of the subcommand and is present in the in-container Docker daemon. The tool neither builds nor pulls it. Image names and source: `TBD` (open item).
- For `install`: the target env folder of the manager exists in the workspace. The tool does not create it; if it is missing the tool reports it and exits 125.

## Interaction

1. Agent runs `run_ephemeral_container run -- <command>` or `run_ephemeral_container install <manager>`.
2. Tool validates the arguments (subcommand, and for `install` the manager) and checks the preconditions (daemon reachable, fixed image of the subcommand present, `/workspace/.output` present, for `install` the target env folder present). It reports a mismatch and stops.
3. Tool creates the run output folder `/workspace/.output/<runID>`.
4. Tool creates (does not start) `ephemeral-<runID>` with the fixed settings below.
5. Tool inspects the created container and verifies the settings on the inspected container, not from its own request. On any mismatch it removes the container and stops.
6. Tool starts the container, streams its stdout and stderr to the caller and into `/workspace/.output/<runID>/`, and waits for it to end or for the timeout. The tool does this from the agent container side; this holds for `install` too, which has no read-write `.output` mount.
7. On timeout the tool kills the container.
8. Tool removes the container and reports the result.

## Ephemeral container settings (fixed)

Applied by the tool to every run; not selectable by argument.

Common to both subcommands:

- capabilities: all dropped (`--cap-drop ALL`), plus `no-new-privileges`;
- user: the agent UID/GID 1001, so files written to the workspace have the same single owner as the rest of the workspace (USS-003);
- root file system read-only, with a `tmpfs` at `/tmp`;
- no credential mount, no Docker socket, no other agent-container path mounted;
- bounded memory, CPU and process count; values `TBD`, and they must fit inside the agent container's own bounds (SSR-AGC-012);
- removed when the run ends (`--rm` semantics, enforced by the tool's own cleanup as well).

Per subcommand:

| Setting | `run` | `install` |
|---|---|---|
| Image | Fixed image of `run` (`TBD`) | Fixed image of `install` (`TBD`) |
| Entrypoint / command | The agent's `<command>` | Manager binary set by the tool; agent supplies only `<manager args...>` |
| Mounts | `/workspace` read-only at `/workspace`, except `/workspace/.output/<runID>` read-write at `/workspace/.output` (covers `src/` and all `/workspace/.*` folders read-only) | `/workspace` read-only at `/workspace`, except the target env folder(s) of the manager, read-write; no read-write `.output` mount |
| Network | none (`--network none`); no host networking, no attachment to any network | `TBD` (open item; registry access conflicts with `--network none` and `--bridge=none`) |
| Log capture | Stdout/stderr streamed by the tool into `/workspace/.output/<runID>/` | Same; done by the tool from the agent container side |

Note on `install`: "no code executed" holds only for the agent's own code. Package managers can execute package code during install (npm lifecycle scripts, Python build backends / `setup.py`, conda post-link scripts). Mitigations to evaluate are in the open items.

## Agent container dependency (summary)

Running a Docker daemon inside the agent container needs `SYS_ADMIN` (mounts, namespaces, cgroups) on the agent container's capability allowlist (SSR-AGC-009). It is held by the gVisor Sentry, not by the `agent-host` kernel. `NET_ADMIN` (bringing up the loopback interface of a `--network none` container) was dropped from the allowlist (decision 2026-10-29) and is an open item: add it back to SSR-AGC-009 only if the ephemeral container's loopback or network bring-up fails without it. `NET_RAW` stays absent; no bridge or NAT is used inside, so runsc's `--net-raw` is not needed and the host runtime configuration stays unchanged. The minimum allowlist is not yet measured (open item, shared with USS-002).

## Acceptance criteria

- `run_ephemeral_container run -- <command>` runs the command and exits with the command's exit code.
- `run`: `docker inspect` of the ephemeral container, taken before start, shows network mode `none`, no capabilities, `no-new-privileges`, a read-only root file system, user 1001, `/workspace` read-only and `/workspace/.output/<runID>` as the only read-write mount.
- `run`: a write by the command anywhere under `/workspace` other than `/workspace/.output` fails.
- `run`: any network access attempted by the command fails.
- `install`: `docker inspect` taken before start shows no capabilities, `no-new-privileges`, a read-only root file system, user 1001, `/workspace` read-only, the target env folder(s) of the manager as the only read-write mount, no `.output` mount, and the entrypoint set to the manager binary. Network mode: `TBD`.
- `install`: a write anywhere under `/workspace` outside the target env folder fails.
- `install`: the manager's exit code is the tool's exit code; a package installed into the target env folder is present there after the run.
- The command's (or manager's) stdout and stderr are in `/workspace/.output/<runID>/`.
- After the run, no container `ephemeral-<runID>` exists, also after a timeout or a failure.
- The agent container's settings, network arming and the host are unchanged by the run.

## Failure cases

Exit codes: the command's (or manager's) own exit code on a completed run; `124` timeout; `125` usage error or tool/daemon failure before the command starts.

| Case | Behaviour |
|---|---|
| Missing or invalid arguments | Usage error, exit 125; nothing is created |
| Unknown subcommand | Usage error, exit 125; nothing is created |
| Unknown manager (`install`) | Usage error, exit 125; nothing is created |
| In-container Docker daemon unreachable | Report, exit 125 |
| Fixed image of the subcommand not present in the in-container daemon | Report, exit 125; the tool neither builds nor pulls it |
| `/workspace/.output` missing or run folder cannot be created | Report, exit 125; nothing is started |
| Target env folder missing (`install`) | Report, exit 125; nothing is started |
| Inspected settings differ from the fixed settings | Remove the container, report, exit 125; the command is never started |
| Timeout reached | Kill and remove the container, report, exit 124; output written so far is kept |
| Command or manager fails | Remove the container, exit with its exit code; output is kept |
| Cleanup / rollback | The run removes only the container it created; `/workspace/.output/<runID>/` is always kept |

## Open items

- Image names and source for the per-subcommand images (preloaded fixed set vs. pulled through the egress policy).
- Network for `install`: registry access conflicts with `--network none` and the daemon's `--bridge=none`. Candidate: `--network host`, which shares the agent container's network namespace, so traffic is still filtered by the host-side controls of USS-004, but exposes the agent's network route to the install process. Alternative: a preloaded/offline package mirror. Not decided.
- Install-time code execution: package managers can run package code during install. Mitigations to evaluate: `npm --ignore-scripts`, `pip --only-binary=:all:`; conda post-link scripts `TBD`.
- Further subcommands (e.g. `test`, `debug`) and the full manager set.
- Default timeout and the memory, CPU and process limits.
- In-container storage driver (`overlay2` vs `vfs`) under gVisor; not set in the image's `daemon.json` yet (open item there too). The data root is the 2g `tmpfs` at `/var/lib/docker`, which counts against the agent container's memory bound.
- Implementation of `run_ephemeral_container` and its installation in `Dockerfile.agent` (not yet implemented).
- Measured minimum capability allowlist of the agent container (shared with USS-002).
- The docker-group membership of the agent user is recorded as a declared deviation in SSR-AGC-011; the tool itself has no requirements yet. The sandbox checks only that `docker` is among the agent user's groups, not that the agent user is its only member.
